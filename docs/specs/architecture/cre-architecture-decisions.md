# CRE — Architecture Decisions (v2.13, 2026-11-24)

Aligned with Requirements & Use Case Specification v1.14 (23 Nov 2026) and Database Design v1.1 (23 Nov 2026).
Document: `architecture/v2.3/cre-architecture-v2.3.docx` / `.pdf` (v2.3 resolves the database schema, optional backup and export expiry: AD-23 – AD-26).

Database Design v1.1 was written against v2.10. Its three changes to this set — snapshot as rows, rounding per version, percentages on the result — are carried into v2.12 as AD-16 (updated), AD-17 (updated) and AD-23. v2.12 adds AD-26 (backup is optional) and nothing in v1.1 contradicts it. v2.13 (24 Nov 2026) fixes three open items: PDF engine = Gotenberg, e-mail provider = Brevo (SMTP relay), session lifetime by env defaults; and sets the production domain (conriskexpert.com) and the backup repository type (S3-compatible).

## Stack
- Frontend: Next.js (TypeScript)
- Backend: Go + chi (api) and Go worker — same module, separate binaries (`cmd/api`, `cmd/worker`, `cmd/migrate`)
- Database: PostgreSQL 16 — schema fixed in **Database Design v1.1** (29 tables; see “Database” below)
- Queue + shared short-lived state: Valkey + asynq (compose service renamed `queue` → `valkey`)
- Object storage: RustFS (S3-compatible; beta — app uses only the S3 API, so MinIO / cloud S3 are drop-in)
- Reverse proxy: Caddy 2 (automatic HTTPS)
- PDF rendering: Gotenberg 8 (Chromium HTML → PDF), its own container, called only by the worker
- External: Google Sign-In (OAuth 2.0 / OpenID Connect); e-mail service for OTP: **Brevo** SMTP relay in production, Mailpit in local/dev; off-site S3 backup repository (different provider or region, only when backup is enabled)
- Runtime: Docker Compose now → Kubernetes (RKE2 / k3s) later

## Networking & routing
- `public-net`: Caddy only (:80/:443 published). `private-net` (`internal: true`): web, api, worker, db, valkey, rustfs, gotenberg, migrate (+ mailpit in dev), plus backup when enabled. `egress-net` (bridge, no published ports): **api and backup only** (backup only while its profile is on) — outbound HTTPS to Google, SMTP (STARTTLS, port 587) to Brevo, and HTTPS to the off-site backup bucket. worker, web and gotenberg have no internet access.
- Caddy: `handle /api/v*` → `api:4000` (path not stripped); `handle` → `web:3000`. Same origin → no CORS.
- Browser calls `/api/v1/...` (relative). Next.js server code calls `http://api:4000/api/v1/...` directly and forwards the auth cookie.
- K8s: egress-net → NetworkPolicy allowing egress 443 (+ mail port) from api pods, and 443 to the backup bucket from the backup job only when backup is enabled.

## Database
- **Schema:** 29 tables in three groups, BCNF, all columns, keys, checks and indexes in Database Design v1.1.
  - Indicator catalogue (12): `locale`, `dimension`, `dimension_text`, `factor`, `factor_text`, `indicator`, `indicator_text`, `ri_e_option`, `ri_e_option_text`, `impact_table`, `advice_item`, `advice_item_text`.
  - Projects and assessments (11): `island`, `project_type`, `project`, `assessment_version`, `version_rl_threshold`, `version_impact_threshold`, `answer`, `answer_y3`, `risk_result`, `result_advice_list`, `strategy_choice`.
  - Accounts, jobs and audit (6): `account`, `job`, `report_job`, `export_job`, `export_job_account`, `audit_log`.
- **Keys and naming:** singular snake_case, `timestamptz` in UTC. User/job rows use a UUIDv7 generated by the api; catalogue rows use natural codes (`EC-MG-1`, `RI_C`, `th`).
- **Fixed sets vs data:** PostgreSQL enums for sets that code branches on (`user_role`, `account_status`, `indicator_direction`, `impact_code`, `advice_list`, `version_status`, `cost_unit`, `time_unit`, `risk_level`, `risk_strategy`, `job_kind`, `job_status`, `export_scope`, `audit_action`). Lookup tables for sets that are data (islands, project types, y3 options and their scores).
- **Localised text:** only text with no code of its own is stored per locale (`dimension_text`, `factor_text`, `indicator_text`, `ri_e_option_text`, `advice_item_text`). `th` is required; other locales fall back to `th`.
- **Integrity:** foreign keys `on delete restrict`; cascade only for `advice_item_text`, `answer_y3`, `risk_result` children (`result_advice_list`, `strategy_choice`). Checks cover threshold patterns, score ranges, level/RM agreement and date/value rules. The advice `(indicator_code, list, position)` unique key is deferrable for reordering.
- **Roles:** schema owner (migrate) and application (api, worker). The application role has INSERT + SELECT only on `audit_log`; it cannot UPDATE, DELETE or TRUNCATE it. Backup has its own S3 credentials.
- **Migrations:** versioned, embedded SQL; idempotent and backward-compatible (expand → migrate → contract), runnable as a Job.
- **Soft delete:** `deleted_at` on projects, versions and accounts; repository filters. Nothing is physically deleted except advice items an admin removes and expired export files.
- **Indexes:** the seven in Database Design v1.1 §4.5 (`project_owner_ix`, `job_requester_ix`, `job_expiry_ix`, `report_job_version_ix`, `audit_log_time_ix`, `audit_log_admin_ix`, `audit_log_target_ix`). Version, answer and result reads use their composite primary keys.

## Accounts, sign-in, sessions
- Sign-up: e-mail + password + 6-digit OTP, or Google. No personal names; organisation optional. Account required for every feature.
- OTP (sign-up and password reset): hashed, 10-minute TTL, 5 wrong attempts, resend once per 60 s. **Pending sign-up lives in Valkey only**; the account row is created in Postgres after verification.
- OTP e-mail is sent synchronously by the api through one SMTP `Mailer` adapter (short time-out): Mailpit in local/dev, Brevo SMTP relay in production — same code, different `SMTP_*` env. Sending domain authenticated with SPF + DKIM (+ DMARC). Alternative not taken: `mail` queue on asynq (worker would need egress).
- Google: OIDC authorization-code flow with PKCE run by the api. `state`, `nonce`, PKCE verifier and intent (login / signup / link) in Valkey, 10-minute TTL. ID token validated server-side (signature via cached JWKS, iss, aud, exp, nonce, verified e-mail). No Google script in the browser. Existing e-mail → Google id linked. New Google user → pending entry in Valkey until the retention notice is accepted.
- Link / unlink Google from the account page; Google id unique across accounts; unlink only if a password exists.
- Session: JWT in httpOnly, Secure, **SameSite=Lax** cookie, `path=/`. CSRF token + Origin check on state-changing requests.
- **Session lifetime (env defaults):** `SESSION_TTL=12h`; with *keep me logged in* `REMEMBER_TTL=30d`. Log out ends the current device only; password reset, deactivate and delete still end every session through the session version. Changed by env, no code change.
- **Server-checked sessions:** the JWT only identifies the user and carries a session version. Middleware loads status, role and session version on every request (Valkey cache, short TTL; Postgres on miss). Password reset, deactivate, delete raise the session version → old sessions get 401. Role comes from the record, not the token.
- Passwords: Argon2id. Rate limits (log in, register, OTP, reset) per IP and per e-mail, counters in Valkey.

## Backend layers (dependencies point downward only)
1. HTTP layer — chi router (`/api/v1`, `/admin` group), middleware (RequestID, RealIP trusting Caddy only, Logger, Recoverer, Timeout, JWT + session check, RequireRole/RBAC, CSRF, rate limit in Valkey), handlers (decode/validate DTO → service → JSON)
2. Service layer — Auth, Users, Projects, Assessments, Indicators, Risk Engine, Reports, Jobs, Admin, Audit
3. Data Access Layer (DAL) — repositories (pgx), Audit Repository, migrations; schema-owner and application roles. Integration adapters — queue client, state store client (Valkey), S3 client, Mailer, Google OIDC client
4. Domain layer — Account, Project, AssessmentVersion + Snapshot, Answer (+ y3 options), RiskResult (+ advice lists), StrategyChoice, Dimension / Factor / Indicator (+ texts), AdviceItem, ImpactTable, Job (Report / Export), AuditEntry — **fields per Database Design v1.1**

Admin Service: manage users (list, search, role, deactivate, delete = anonymise; per-user project and version **counts only**); edit advice per indicator; edit RL thresholds (a–e) per indicator; edit the shared RI_C / RI_T tables (one page, both side by side; one save, one audit entry per changed table); request and download pseudonymised research exports. No admin UI for rounding.

## Authorisation and deletion
- Object-level authorisation in services/repositories: every project, version, answer, result, report and job query carries the session user's id. **No admin bypass** — admins cannot open other users' projects, versions, answers, results or reports. Not owned or soft-deleted → 404.
- Repositories for user-facing reads require an owner id and always filter `deleted_at IS NULL`. A separate research read path (export only) includes soft-deleted rows.
- Soft delete (projects, versions): `deleted_at`, no restore, nothing physically removed (report files kept too).
- Account deletion (by user or admin) = anonymise: e-mail, password hash, Google id removed; `status = deleted`; row marked deleted; projects kept. Each account has a random `pseudonym` created at sign-up (not derived from e-mail) that survives anonymisation and is used in exports.

## Versions, snapshot, submit
- Project has versions v1..vn; numbers never reused (unique `(project_id, version_no)`); a new version is always blank; only the latest is editable (stays read-only even if the newer one is later deleted).
- **Snapshot per version — typed rows, not one JSON document.** In the create-version transaction: project value, start/end date and rounding (`snap_score_decimals`, `snap_rm_decimals`) go on `assessment_version`; all 55 RL threshold sets go to `version_rl_threshold`; both RI_C / RI_T tables go to `version_impact_threshold` (2 rows). All scoring of that version reads these rows; threshold and project edits apply only to versions created afterwards. Advice text is **not** snapshotted (results show current advice text via stored list keys). The research export serialises the same rows to `project.json`.
- Answers saved as entered (`value` + `unit`), partial versions allowed; no scores before submit.
- **Submit** (≥ 1 complete indicator): one transaction; for each complete indicator convert units → Risk Engine → upsert `risk_result` (x, y1_pct, y2_pct, RL, RI_C, RI_T, RI_E, RI_max, RM, level) and replace `result_advice_list`; previous results of the version replaced; status draft → submitted. Rounding is already recorded on the version, not repeated per result. Synchronous (milliseconds) — no queue.
- Results view, PDF and export read the stored results of the last submission; nothing is recalculated on read.
- Strategy per H/VH indicator (REDUCE / TRANSFER / AVOID / ACCEPT) stored in `strategy_choice` with the version; changeable in the latest version only.

## Assessments → Risk Engine boundary
- **Risk Engine is pure**: input = X (indicator unit), y1 (% of project value), y2 (% of project duration), y3 (set A–I) + thresholds and rounding from the version snapshot; output = RL, RI_C, RI_T, RI_E, RI_max, RM, level, advice list keys. No unit conversion, no DB access.
- **Unit conversion lives in the Assessments Service (input layer)**: y1 baht → % (÷ project value × 100), y2 days → % (÷ (end − start) days × 100), using the version's snapshot of project value and dates. It stores value as entered + unit + %, and passes only % to the engine.

## Engine settings
- `score_decimals` (default 2): RL, RI_C, RI_T, RI_E rounded before RI_max, RM and advice selection.
- `rm_decimals` (default 3): RM rounded, then classified.
- **Set by environment variables only** (`SCORE_DECIMALS`, `RM_DECIMALS`) on api and worker — no admin UI (BR-18; supersedes the earlier admin-editable setting). Copied into each new version snapshot; each version records the decimals used. All api replicas must run with the same values.

## Indicator constants
- Thresholds `a..e` per indicator, nullable. Three-threshold indicators (missing values stored as NULL, never 0):
  - **only `a, b, c`** — EC-HS-2, EC-HS-5: RL = 1 if v ≤ a; 1 + (v−a)/(b−a); 2 + (v−b)/(c−b); 5 if v > c (levels VL, L, M, VH).
  - **only `c, d, e`** — EC-HS-1, EC-HS-3, SO-PL-1, EV-EV-2, EV-EV-3 (mirror): RL = 1 if v < c; 3 + (v−c)/(d−c); 4 + (v−d)/(e−d); 5 if v > e (levels VL, M, H, VH). v = c → 3.
  - Risk Engine picks the scoring branch from which thresholds are NULL; any other NULL pattern blocks scoring. Admin constant editing must keep a valid pattern (all five, a–c only, or c–e only) and the right order (inverse indicators decreasing).
- RI_C and RI_T: one shared table each (a–e, ≥ 0, strictly increasing), admin-editable. RI_E option scores fixed, not editable.
- X (likelihood input) is a **number only, ≥ 0** for every indicator (0 allowed, negatives rejected) — no option list. Validate in the API (`x >= 0`), not only in the UI.
- Catalogue (indicators, thresholds, tables, advice) cached in each api replica; invalidated on all replicas via Valkey pub/sub after an admin edit.

## Seed files (v1, 11 Nov 2026)
- `cre-indicators.json` — full seed: `dimensions`, `factors`, `ri_c_thresholds`, `ri_t_thresholds`, `ri_e_options`, `indicators` (with nested `advice`).
- `cre-indicators.csv` — `group_id, f_code, factor_code, name_th, name_en, unit_th, unit_en, a, b, c, d, e, question_x, question_y1, question_y2, question_y3` (empty cell = NULL threshold).
- `cre-advice.csv` — `group_id, list, position, text_th` (one row per advice item; seeded as locale `th`).
- Question columns are named by **input** (`x`, `y1`, `y2`, `y3`); advice lists are named by **score** (`RL`, `RI_C`, `RI_T`, `RI_E`).
- `migrate` seeds insert-if-absent, so admin edits survive redeploys.

## Advice
- Per indicator, four advice lists: `RL`, `RI_C`, `RI_T`, `RI_E` (same names as the engine scores everywhere: DB enum, API, JSON). Source: `indenti 25.10.26 (1).xlsx`, sheet `Indenti.8.11.26`; typos fixed in the seed.
- **Each list has 1–5 items, independent per list** (3 each in today's seed). Store one row per item: `advice_item(id, indicator_code, list ENUM, position 1..5, updated_by, updated_at)`, unique `(indicator_code, list, position)` deferrable, and its text per locale in `advice_item_text(item_id, locale, text NOT NULL)`, unique `(item_id, locale)`. `th` is required; other locales optional and fall back to `th` (FR-56). Enforce 1–5 in the Admin Service (save the whole list in one transaction; reject 0 or > 5 items, or an item without `th` text); CHECK `position BETWEEN 1 AND 5`. API returns arrays; UI and PDF report must not assume 3 items.
- **When:** shown only for indicators at level **H or VH** — a fixed rule, not a per-indicator setting.
- **Which:** `RL >= RI_max` → RL list; otherwise the list(s) of the impact(s) equal to RI_max. **Ties (two- or three-way) → show every tied list**, order RI_C, RI_T, RI_E. So the engine returns 1–3 list keys per indicator; UI/PDF render each with its label. Compare the rounded scores used for RM.
- Indicator questions: one per input — `question_x` (numeric), `question_y1` (cost), `question_y2` (time), `question_y3` (environment); y1 / y2 question text is the description only — the unit (baht / % or days / %) comes from the UI picker.

## Localisation (FR-55–FR-57, NFR-11, AD-22)
- UI ships Thai only (`th`, the default); no language switch until a second locale exists.
- Every user-facing string (web app and PDF template) comes from per-locale message catalogues (e.g. `messages/th.json`); adding `en` needs no code or schema change.
- Dates and numbers via a locale formatter (`th`: Buddhist era; `en`: Common Era). Layouts allow ~30 % longer labels.
- Not translated: risk level codes (VL–VH), indicator codes, units. User-facing copy shows no spec codes (UC/FR/BR/NFR) or internal terms such as “snapshot”.

## Audit log
- Every admin action (user role / deactivate / reactivate / delete, advice edit, RL threshold edit, RI_C / RI_T edit, export request and each export download) → one `audit_log` row: time UTC, admin id, action, target type + id, old and new values (`jsonb`), request id, IP (`inet`).
- Written **in the same transaction** as the change (Admin Service → Audit Service → Audit Repository). Export download: entry written before the stream starts.
- Append-only at DB level: two DB roles — schema owner (migrate) and application (api, worker); the application role has INSERT + SELECT only on `audit_log`. Kept indefinitely; revisit monthly `occurred_at` partitions at about 10 GB / 50 million rows.
- Request id and client IP come from middleware via request context; RealIP trusts only Caddy.

## Jobs: reports and research export (async)
- One job model (Jobs Service): `job` row in Postgres (source of truth: queued / running / done / failed / expired) + asynq queue (`reports`, `exports`). Status visible to the requester only.
- Report: api enqueues → 202 + job id → worker builds data from stored results + advice + strategies, renders HTML template → PDF via **Gotenberg** (`POST http://gotenberg:3000/forms/chromium/convert/html`; `index.html` + CSS + Thai font files sent as assets in the same request, so no custom Gotenberg image), uploads `reports/{id}.pdf`, marks done → client polls → downloads through api (session + ownership check, stream). Repeated request for the same submission returns the existing job.
- Export (admin): `job` + `export_job` (+ `export_job_account`) and audit entry in one transaction → enqueue → Export Builder (all / selected users, optional soft-deleted data; e-mail and Google id removed; account → pseudonym; organisation kept) → one ZIP (`user.json`, `project.json`, one CSV per version) at `exports/{id}.zip` → download through api (admin role, audited). `expires_at` = finish + 7 days; after that the endpoint returns 410 and a daily 03:00 sweep deletes the object and marks the job expired. Export files are not backed up.
- Worker scales and is resource-limited independently of the api; separate concurrency per queue so exports cannot starve reports.

## Backup and recovery (optional)
- **Enable / disable:** a single `BACKUP_ENABLED` flag in `.env` is mapped by the deploy wrapper to both sides. True adds the `backup` Compose profile and sets `db.archive_mode=on`; false omits the profile and sets `archive_mode=off`. Production default is true; local/dev default is false. A preflight check rejects the two mismatch states (profile on with archiving off, or profile off with archiving on). It is deployment configuration, not an admin setting.
- **Disabled:** no backup container, no WAL archiving, no full / differential backup, no off-site copy and no `reports/` mirror. Existing off-site backups remain under retention, but nothing new is protected; no RPO/RTO claim. `/readyz` and monitoring report `backup disabled`. Re-enabling starts with a new full backup and a restore check.
- **Switching later:** `archive_mode` is a postmaster parameter, so enabling or disabling an existing database requires a PostgreSQL restart; writes pause for a few seconds. Enabling requires a full backup and a restore check; PITR history starts at that full backup, and nothing before it can be recovered.
- **Targets (when enabled):** RPO ≤ 5 min, RTO ≤ 4 h.
- **PostgreSQL (when enabled):** physical backup with continuous WAL archiving; `archive_mode = on`, `archive_timeout = 60s`. `backup` runs pgBackRest: full every Sunday 02:00 Asia/Bangkok, differential on the other days at 02:00. Retention: 5 full backups with all WAL between them (4–5 weeks of PITR); the first full of each month is copied to a second repository with object lock and kept 12 months. Encrypted (AES-256) and compressed (zstd) before upload; separate credentials.
- **Where:** any S3-compatible bucket (endpoint, region, bucket and keys from env) at a different provider or region — never the app's RustFS on the same host. 3-2-1: live database, off-site repository, monthly immutable copy.
- **RustFS (when enabled):** `reports/` mirrored nightly; `exports/` not backed up (rebuilt by requesting the export again).
- **Valkey:** no backup; only short-lived state. Jobs survive because the `job` table is the source of truth; on start-up the worker re-enqueues queued / running jobs.
- **Restore (when enabled):** PITR to the latest point by default. To undo a mistake, restore to a separate instance and copy the affected rows back; production is not rolled back as a whole. Monthly automated restore test + quarterly full drill.
- **Monitoring:** while enabled, alert when the newest WAL is older than 10 minutes, the last backup older than 26 hours, or `pgbackrest check` fails; while disabled, emit one `backup disabled` warning instead.
- **Deleted accounts in backups:** anonymised e-mail may persist for up to 5 weeks (12 months for monthly copies); the retention notice discloses this. Backups are never used to bring erased data back into production.

## Data placement
- Postgres: accounts, projects, versions (+ typed snapshot rows), answers, results, strategies, catalogue, thresholds, advice, jobs, audit log. No backend volume — api/worker are stateless.
- Valkey: asynq queues + short-lived state (OTPs, pending sign-ups, OAuth state, resend cool-downs, rate-limit counters, session-check cache, cache-invalidation pub/sub). All state keys have a TTL; `noeviction` policy; AOF on.
- RustFS: `reports/`, `exports/` — reached only through the api. Export files expire after 7 days.
- Volumes: `pgdata`, `valkey-data` (AOF on), `rustfs-data`, `caddy-data` (certs). Backups are off-site, not a local volume.

## Scalability
- Stateless tiers (web, api, worker) scale out with replicas; Caddy uses dynamic upstreams + health checks.
- Already shared in Valkey: rate-limit counters, OTP state, session cache, catalogue-cache invalidation. Next.js replicas need same build + `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`.
- Valkey is on the login path → include in api readiness; Sentinel before production scale.
- Stateful tiers: Postgres single primary (scale up → PgBouncer → read replicas / CloudNativePG); RustFS single node. Backup: one per database while enabled; K8s CronJob or the CloudNativePG Barman Cloud plugin only in backup-enabled environments.
- Performance target: interactive requests p95 < 1 s.
